Architectural Design Document

Heatwave Modelling (CHAP) — End-to-End Architecture

This repository is a small Streamlit web application that computes and visualizes a daily heat‑index surface for Northern Nigeria (1980–2025). All heavy computation runs server‑side inside Google Earth Engine (GEE): the app pulls the public ECMWF/ERA5/DAILY reanalysis collection, clips it to a user‑owned Nigeria boundary asset, derives relative humidity from 2 m air temperature and dewpoint temperature, applies the NWS Rothfusz heat‑index regression, and renders the result as an interactive folium/geemap map with a date‑picking UI — there is no local database, ETL job, or trained ML model in this codebase; the entire pipeline lives in two Python files.

1 Data Sources

ERA5 Daily reanalysis (ECMWF, via Earth Engine)

Two bands are pulled from the public ECMWF/ERA5/DAILY ImageCollection: mean_2m_air_temperature and dewpoint_2m_temperature, filtered to the date range 1980-01-01–2025-09-15.

Northern Nigeria boundary asset

An ee.FeatureCollection hosted as a private GEE asset under a personal project (ee-victoridakwo), used both to clip the ERA5 imagery and to draw the outline layer on the map.

2 Ingestion

Two independent entry points, no shared ingestion module

gee.py exposes a standalone init_ee() helper meant for ad‑hoc / CLI use: it tries ee.Initialize(project=GEE_PROJECT) (project id continual-apex-435201-h6) and falls back to an interactive ee.Authenticate(auth_mode="localhost") flow. It is not imported by the Streamlit app — the two files do not share auth code.

nigeria_heat_index.py instead builds its own service‑account credentials inline (lines 19‑42) with scope https://www.googleapis.com/auth/earthengine, selecting between the three credential sources listed above, then calls ee.Initialize(credentials). It also monkey‑patches sys.modules["blessings"] with an empty module before importing geemap, worked around explicitly to avoid an import failure on Streamlit Community Cloud (comment: "Fix blessing issue for Streamlit Cloud").

Once authenticated, "ingestion" is really an Earth Engine query: ee.ImageCollection(...).select(...).filter(ee.Filter.date(...)).map(lambda image: image.clip(boundary)) — no bytes are downloaded into this repo or process; GEE builds a lazy server‑side computation graph.

3 Storage

No local persistence layer exists in this repo. There is no database, no Parquet/CSV output directory, and no cache of computed rasters. All data at rest lives in Google's infrastructure: the public ERA5 catalog and the user's own GEE asset (projects/ee-victoridakwo/assets/Northern_Nigeria). Within a single app run, intermediate results (relative humidity, heat index) exist only as unmaterialized GEE ee.Image/ee.ImageCollection objects — evaluated lazily and only rendered as map tiles when Map.addLayer/Map.to_streamlit is called. .gitignore confirms the only file-based storage the project anticipates is local, gitignored secrets (.streamlit/secrets.toml, keys/*.json, *.pem) — never modelling data.

4 Transformation / Modelling

Step 1 — Relative humidity (approximation)

For each daily temperature image, compute_relative_humidity() looks up the same‑day dewpoint image and applies RH = 100 - 5 * (T - D) directly on the raw Kelvin bands (a linear dewpoint‑depression approximation, not a psychrometric formula), producing a relative_humidity band added to the temperature image.

nigeria_heat_index.py:65-76

Step 2 — Heat index (NWS Rothfusz regression)

compute_heat_index() converts mean 2 m air temperature from Kelvin → Celsius → Fahrenheit, then applies the standard 9‑coefficient NOAA/NWS Rothfusz regression (c1..c9, e.g. -42.379, 2.04901523, ...) against temperature (°F) and the previously computed relative humidity, producing a heat_index band.

nigeria_heat_index.py:79-98

All modelling logic executes as Earth Engine server‑side expressions (ee.Image.expression) mapped across the ImageCollection — there is no NumPy/pandas/scikit‑learn model training pipeline in the repo, despite pandas/numpy being present in requirements.txt as transitive dependencies of the geospatial stack.

5 QC / Validation Not present

No automated tests, no CI workflow (.github/ does not exist in this repo), and no explicit data‑quality checks (missing‑image handling, range/sanity checks on temperature or relative‑humidity values, cloud/no‑data masking) appear anywhere in gee.py or nigeria_heat_index.py. The try/except in gee.py (lines 10‑14) only guards Earth Engine authentication failures, not data quality. This is stated as an observed gap, not inferred from convention.

6 Output / Consumers

Interactive Streamlit app

nigeria_heat_index.py is the single user‑facing deliverable: st.set_page_config, a three‑column slider UI for Year/Month/Day (1980‑2025, 1‑12, 1‑31), and a geemap.foliumap.Map centered on Nigeria ([10, 9], zoom 6) rendered in‑page via Map.to_streamlit(height=700).

nigeria_heat_index.py:103-128

Map layers & legend

A heat‑index layer (palette blue→cyan→green→yellow→orange→red→purple, range 0‑150°F) filtered to the selected date, an outline layer for the Northern Nigeria boundary, and a custom HTML/CSS gradient legend injected via st.markdown(..., unsafe_allow_html=True).

nigeria_heat_index.py:117-164

Deployment target

The credential‑selection order (Streamlit secrets first, then EE_SA_JSON env var, then a local key file) and the explicit "blessings" workaround comment indicate the app is designed to run on Streamlit Community Cloud, with a CI/CD or GitHub Actions path as a secondary supported environment, and local development as a third.
