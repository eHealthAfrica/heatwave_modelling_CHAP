<objective>
Build `heatwave/batch.py` — the Earth Engine asynchronous batch-export harness (toAsset submission,
resumable task-state file, task polling, paginated asset read-back, CSV writing) — stand up
`tests/test_export.py` (the EXPORT-04 test file), and then **actually prove the round-trip live**
against `heatwave-508110` before any other plan builds on top of it.

Purpose: 04-RESEARCH.md's entire export strategy rests on one assumption it explicitly flagged as
`[ASSUMED, MEDIUM confidence]` — that this project's service account can write a **new** Earth Engine
table asset (Environment Availability table) — plus one unanswered question (Open Question 3: does
paginated `toList(pageSize, offset).getInfo()` read-back actually work as expected). If either is
wrong, D-07 forbids the `toCloudStorage()` fallback and Pitfall 1 blocks `toDrive()`, and the phase's
whole approach needs rethinking. This plan de-risks both **first**, at tiny scale, in Wave 1.

Why `heatwave/batch.py` rather than putting this harness inside `scripts/run_batch_export.py` (which
is where 04-RESEARCH.md's "Recommended Project Structure" sketched it): EXPORT-04 requires these
mechanics to be covered by `tests/test_export.py`, and a bare script under `scripts/` is awkward to
import from a test. CONTEXT.md gives Claude's discretion over "exact polling/resume mechanics for the
async batch task (D-04)", which this split falls under. `scripts/run_batch_export.py` (plan 04-04)
stays exactly as CONTEXT.md describes it — the production CLI entry point — and composes this module.

Scope boundary (important for the verifier): this plan proves the **mechanism** on a handful of rows.
It does not run, and must not be expected to run, the full 1991-present 4,841-ward historical backfill.
That is a separate, deliberate, hours-long manual invocation that happens after this phase's plans are
verified (see 04-VALIDATION.md "Manual-Only Verifications").

Output: `heatwave/batch.py`, `tests/test_export.py`, updated `.gitignore`.
