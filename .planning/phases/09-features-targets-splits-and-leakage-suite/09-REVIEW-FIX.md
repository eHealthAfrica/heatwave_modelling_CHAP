## Fixed Issues

### WR-01: `_check_store` does not bind the store to the panel
**Files:** `heatwave/forecast/dataset.py`, `tests/forecast/test_forecast_dataset.py`
**Commit:** d51b2b0
**Fix:** `_check_store` now rejects a store whose `data_sha256` differs from the panel, whose week axis differs, or whose array shapes differ from (wards, T). Test: a store built from a poisoned panel with the same wards and fit_end is rejected by `lead_rows` and `build_issue_table`.
**Deviation:** the suggested `clim_fit_range["data_sha256"] == panel.sha256` check was not added. `test_row_level_truncation` (leakage suite) deliberately reuses one train_end climatology across truncated panels, so that comparison would break a locked leakage test. The store-level `data_sha256` check covers the stale-cache scenario.

### WR-02: issue-table `split_l{k}` ignored embargo and warm-up
**Commit:** d57f67a
**Fix:** `splits.issue_split_labels` (train, embargoed, validate, test, beyond_test); `build_issue_table` also labels warm-up origins `warmup`. Test checks the labels at the embargo and warm-up boundaries and that `split_l{k} == "train"` with `has_label` equals `lead_row_index(..., "train")` for every lead.

### WR-03: memory on the full panel
**Commit:** d7f9e07
**Fix:** `ward`, `last_obs_week`, `target_week*` and all split columns are pandas Categoricals built from integer codes (no per-row strings); `pd.DataFrame(cols, copy=False)` avoids the consolidation copy in both `lead_rows` and `build_issue_table`; `build_issue_table` raises above `max_rows` (default 3,000,000) with a message to pass `origin_positions`/`ward_positions`. Test: no object-dtype columns, categoricals present, split columns compact, guard raises.

### WR-04: `assign_split` raised past the test years
**Commit:** 2471edf
**Fix:** `assign_split(..., strict=False)` labels targets at or after the end of the test years `beyond_test`; `split_masks` uses it (beyond_test matches no mask, so it is never modelled); `build_issue_table` and `report.prevalence_tables` use it (the report adds a `beyond_test` row only when present). Default `strict=True` behaviour is unchanged. Tests: a panel extended to 2027-W10 builds the issue table, prevalence tables and row-count table; modelling rows never include beyond_test targets.

### WR-05: feature cache
**Commit:** 0a44f7f
**Fix:** `feature_code_version()` (sha256 of features.py, climatology.py, registry.py, weeks.py with normalised newlines) in the meta; `registry_names` is a required argument of `load_feature_store`; arrays are written to `*.tmp` then `os.replace`d, and the old `store_meta.json` is removed before any array is touched; per-array sha256 in the meta, verified on load. Tests: each mismatch (code version, missing/removed hash, registry names, corrupted-but-parseable array) is a cache miss; an interrupted save leaves no meta and no half-written array.

### WR-06: `dataset` hard-wired to the global `REGISTRY`
**Commit:** 5874cae
**Fix:** `registry=REGISTRY` on `lead_rows`, `build_issue_table`, `_feature_names`, `_gather_features`, `_issue_features`. Test: a copied registry with an extra feature reaches the rows and the issue table, and values match; the global registry still rejects the unknown name.

### WR-07: report script path safety
**Commit:** 7c96227
**Fix:** `--docs-out` must be under `docs/` unless `--force` (frozen, outputs/, keys/ stay forbidden even with `--force`); an existing file is only overwritten if it carries the `<!-- generated by scripts/forecast_data_report.py -->` marker (or is the default report path), unless `--force`. When `--expected-parquet-sha256` differs from the pin in forecast.yaml, the script warns on stderr, adds a "pin overridden" line to the report provenance, and writes `pin_override` to the run manifest. Existing script tests now pass `--force` for tmp output paths. `docs/forecast/DATA_REPORT.md` regenerated with the real script (commit 29bf040): only the run id, timestamp and marker line changed; all numbers are identical.
